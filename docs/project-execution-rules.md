## 3. 数据权威与覆盖范围

- **用户已确认：开发阶段以本机为唯一权威来源，每次开发发布全库覆盖所选远端。**
- 覆盖包含设备、类别、配置、工具、附件、映射、价格、图片引用，也包含账号、分享、询价、报价及其他库内记录。
- 远端独有记录不会合并保留在新库中；只能通过覆盖前的独立备份恢复。不得执行双向 SQLite 文件同步。
- 同步范围已确认，不再把“全库还是目录增量”列为待选问题；但目标身份、访问方式和实际运行数据卷仍须核实。
- 正式接入真实客户业务前重新确认数据权威和发布策略，不能把开发阶段全库覆盖默认延续到生产。

## 4. 静态资源和图片

| 资源 | 管理和发布规则 |
| --- | --- |
| 页面 Logo、字体、实际使用的静态产品图片 | 纳入 Git；按 `.gitattributes` 使用 LFS，目标必须拉取实体文件，不能发布 LFS 指针 |
| 后台上传图片 | 不进 Git；随全库备份同步至目标上传目录，保留相对路径，校验哈希和数据库引用 |
| PSD、Excel、原图和压缩包等源资料 | 独立保存、备份；不得作为网站发布资源，不盲目整目录提交 |
| 数据库、备份、私有配置、测试截图及 PDF 样稿 | 不进 Git，不进入静态站点或镜像公开层 |

- `tb/configpic` 存在未跟踪的图片与源资料，须先核对实际引用，再决定哪些发布图纳入 Git/LFS。
- 本机上传目录缺失不能直接理解为“无需图片”；必须先确认当前配置和所有库内引用。
- 源图片缺失、路径非法、LFS 实体缺失或哈希不一致时中止发布，不报告成功。
- 远端独有图片不自动删除；同名文件若需覆盖，先备份。清理孤立资源是独立操作。

## 5. 每次开发发布的顺序

1. 明确源仓库提交、源库、目标主机、项目目录、数据卷及维护窗口，核对未提交资源。
2. 暂停源端目录/图片编辑或采取一致性措施；用 SQLite 在线备份生成源库快照，不直接拷贝正在写入的库文件。验证完整性、外键、迁移版本和图片引用。
3. 停止目标写入，备份目标库和上传图片；记录恢复位置。备份失败禁止继续。
4. 上传到独立暂存区并校验文件；代码、静态图片、数据库快照和上传图片作为同一发布批次。
5. 通过确认式恢复工具替换目标库，同步图片；保留服务器私有 `.env`、备份目录和数据卷。
6. 重建 `web` 和 `api`，运行统一 Alembic 迁移；不使用未经核验的 `stamp` 绕过结构差异。
7. 验证 ready、完整性、外键、关键记录数量/内容、静态图片、上传图片、敏感路径拒绝及 PDF Logo；验证页面和业务链路。
8. 记录目标、时间、Git 提交、备份位置、验证结果及失败项；验证失败应保持维护状态或按已验证备份回滚，不宣布成功。

目前这些是执行要求，**自动打包/同步/发布机制尚未实现**，不能把文档中的流程描述成已配置的定时或自动任务。
