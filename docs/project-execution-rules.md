## 0. 正式数据与发布强制原则（2026-09-13）

运行配置更新：本机 `deploy.local_dev_server` 已默认 NAS 模式，入口 `127.0.0.1:8082`，仅启动前端代理到 `192.168.31.69:8080`，页面有正式数据可写提示；不自动启动本机 API。独立模式显式使用 `--mode isolated`（默认 8081）。两种端口隔离浏览器存储，禁止在原隔离端口 8081 启动 NAS 模式。以下“尚待实施”仅为制定原则时的历史描述，以本段为准；API版本自动检测仍未实现。

- NAS 为正式数据唯一来源，产品、用户、上传图片及业务记录统一由 NAS API 管理。本机前端不直接打开共享 SQLite 文件，不复制本机会话，不用本机调试库覆盖 NAS。
- 本机前端连接 NAS 时，保存、删除、上传和发送均是真实操作，仍受现有账号权限限制；不能以本地域名视为测试授权。应显示“NAS 正式数据，可写”，隔离模式保留独立登录；这两项运行配置/提示尚待实施。
- API、权限、数据结构及破坏性测试使用隔离后端和 NAS 备份副本，测试数据不得回灌正式库。日常发版仅更新获准代码、静态资源和必要的版本化结构迁移，不同步本机产品/账号数据。
- 每次发布必须比较 NAS 实际部署基线与待发布版本，检查路由、请求/响应模型、鉴权、服务逻辑、依赖、数据库 schema、Alembic revision 和启动迁移脚本，不能只看迁移文件是否新增。NAS 无 Git 时用已部署文件清单/哈希比较；基线或影响不明则暂停，不能宣称无变更。
- 每次 NAS 发布在同步前必须根据文件清单、内容哈希和镜像影响分类为“快速部署”或“全量覆盖”。仅 HTML/CSS/JavaScript、既有静态图片或单一服务内部源码的小型修改，且 Dockerfile、基础镜像、依赖锁定、构建参数、入口脚本、Compose、API 契约和数据库结构均无相关变化时，使用 Docker 缓存并只重建受影响服务；纯前端默认执行 `docker compose build web` 和 `docker compose up -d --no-deps --force-recreate web`，不得惯例性增加 `--no-cache` 或重建 API。
- 增量发布清单不得仅凭肉眼或手工挑选少数表面修改文件。必须从待发布 Git 差异出发，补齐 HTML 引用的 CSS/JavaScript、CSS 引用的图片/字体、运行时模块及构建上下文中的相关依赖，形成完整的发布依赖闭包；必要时对全部 Git 跟踪的目标服务运行文件生成清单和 SHA-256。同步前核对本机候选与 NAS 源码，同步后再核对 NAS 源码与运行容器，三层一致后才能进入页面/接口验收。缺失文件、旧哈希或无法确认的引用均视为发布不完整，禁止以构建成功代替一致性证明。
- Dockerfile、基础镜像、Python/系统依赖、约束文件、构建上下文规则、入口脚本或 Compose 构建配置变化，以及缓存异常、线上文件哈希与候选版本不一致、需要验证从零可重现构建时，才升级为全量覆盖或对受影响服务执行 `--no-cache`。能限定为单一服务时不得扩大到全部服务；无缓存构建不是普通发版默认项。
- 快速部署后必须核对线上资源/API 与候选文件哈希、内容类型、健康检查和受影响页面。验证失败先停止宣布完成，定位同步、构建或缓存层；只有证据指向构建缓存时才对相应服务无缓存重建。
- **每次 NAS 部署后，代理/执行者必须主动提醒用户完成发布后验证，并给出与本次影响范围对应的可执行检查命令或检查项。** 最低检查包括 `docker compose ps`、相关服务日志、`/api/v1/ready`、候选文件或接口版本一致性及受影响业务页面/流程；涉及 API 时还要验证关键接口，涉及数据库时还要验证 revision、完整性、外键和必要业务数据。未提醒、未执行或结果未返回时只能记录为“部署已执行、待验收”，不得宣布发布完成。
- **发现 API 或数据库变化，必须在重建 API、启动可能自动迁移的容器或正式写入之前提醒用户，并取得该变更发布的明确确认。** 提醒包含变更摘要、兼容影响、当前/目标迁移版本、是否停机、隔离验证结果、备份及回退方式。只发前端时也须声明 API/数据库未变及核对依据。
- 先上线兼容旧前端的 API/结构扩展，再上线依赖它的页面。删字段、改字段含义、数据重算、非兼容 API 必须单独制定维护与回退方案；代码回滚不代表数据库可安全降级。
- 本机启动或刷新不得触发 NAS 升级。现有 API 容器入口可能自动执行 Alembic，所以重建/启动 API 本身也必须先通过上述门禁。没有备份、隔离演练或明确确认则不执行。
- 提醒属于每次发布时必须执行的人工/代理检查清单，不是已安装的自动通知或 CI 阻断器。任何未来发布脚本也必须遵守；自动检测机制尚未实现。

## 3. 历史专项数据合并规则（非日常发版流程）

以下为 2026-09-12 专项迁移留档，已被第 0 节取代为非默认流程。只有用户再次明确授权专项数据导入、并重新确认来源和冲突策略时才可参考；不能沿用旧“本机优先”授权自动覆盖正式数据。

- **现行规则：产品信息、用户账号以本机为准新增或覆盖同一记录，NAS 独有记录保留。** 这不是全库替换，也不是先清空表再导入。仍须先只读检查 NAS 数据库、上传图片和迁移版本，在隔离副本中完成兼容性合并；不得因本机缺失而删除 NAS 数据。
- 产品信息包括设备、颜色、参数、设备图片、基本/可选配置、配置类别、维修工具、附件、关联映射、价格、排序、启用状态、双语内容及语言可见性。同步其实际引用的图片实体，不能只更新数据库路径。
- 用户账号包括身份联系方式、个人资料、密码哈希、角色与启用/停用状态等账号字段；已确认属于同一账号的内容差异按本机覆盖，不另外按更新时间选择。不得导出明文密码；不复制本机会话/登录令牌。覆盖导致凭据、角色或账户状态改变时，使该 NAS 账号的旧会话失效，其他 NAS 独有账号不受影响。
- 迁移前必须取得本机与 NAS 的一致性备份，分别核对数据库完整性、外键、迁移版本、业务单号、身份数据、图片引用和文件哈希，并输出新增、相同及冲突清单。
- 结构变更先在隔离副本通过 Alembic 兼容；身份/记录对应关系确认后，无歧义的新增和本机覆盖项可自动应用，并记录覆盖前后差异。同 ID 异实体、同编号异产品、同邮箱/手机号异账号、跨目录归属或唯一约束冲突必须逐项确认，不凭显示名称或单一碰撞字段自动认定同一对象。
- NAS 独有的产品、账号、目录条目、关联和上传图片保留。对 NAS 已有记录优先保留其主键及业务引用，必要的 ID 映射必须显式记录并完整验证；版本字段保持兼容，不直接回退并发版本。本机启停设置只覆盖已匹配记录，不级联删除 NAS 独有子项。
- 本次同步不覆盖 NAS 购物车/保存配置、分享、询价、报价、历史快照、发送记录或审计等业务数据，也不顺带导入本机测试业务记录；保留业务单号、分享码、归属和关联关系。产品当前资料更新不重写历史快照。
- 图片同路径同哈希可复用；同路径异内容须列出冲突并使用不破坏原引用的路径映射，保留历史业务及 NAS 独有记录仍引用的实体，不能以本机图片直接覆盖历史图片文件。
- 正式应用前重新读取 NAS 变化并验证幂等；在事务、外键、图片完整性和失败回退都通过后，才可在已授权的维护窗口应用。不得使用双向 SQLite 文件同步或直接复制运行中数据库文件。
- 本规则仅定义 NAS 的长期迁移方式。ECS 或其他目标仍需单独确认目标数据、授权和合并策略，不能从 NAS 结论推定。

## 5. 每次 NAS 发布的顺序（现行）

1. 核对 NAS 当前代码/文件哈希、实际 API 版本、数据库 revision、数据卷及待发布版本；记录 API 和数据库分别“有变更/无变更/无法确认”。
2. 有 API/数据库变更时先按第 0 节提醒用户，提交隔离测试与迁移演练结果并等待明确确认；无法确认影响时停止发布。
3. 备份受影响代码与 NAS 正式数据库/上传资源，确认备份可恢复、维护窗口和回退方案。纯前端发布不得顺带升级 API 或同步数据。
4. 从 Git 差异生成候选文件清单并补齐引用/构建依赖，必要时扫描目标服务全部 Git 跟踪运行文件；核对本机候选与 NAS 源码哈希后再暂存和校验代码、静态资源。保留 `.env`、`data/`、上传实体、历史记录；不把本机数据库放入正式发布内容。旧 release_bundle 的 data 归档不得应用到 NAS。
5. 按确认范围和构建分类发布：快速部署只重建受影响服务并复用缓存；纯前端只重建 web。仅符合第 0 节全量覆盖条件时才对必要服务使用 `--no-cache`。API/结构变化按兼容顺序执行受控 Alembic 升级和后端发布，再更新前端。不得用 stamp 绕过检查。
6. 部署命令结束后主动提醒用户进行发布后检查，并提供与本次范围对应的命令/检查项；至少验证容器状态、相关服务日志、`/api/v1/ready`、本机候选/NAS 源码/运行容器三层文件或接口版本一致性、受影响页面和必要业务流程。涉及 API/数据库时追加关键接口、当前 revision、完整性、外键及必要业务数据检查。记录实际版本、备份位置、结果和待验收项；在用户返回验证证据前标记为“部署已执行、待验收”，不以构建成功或容器启动代替发布完成。
7. 失败时停止后续发布并按已验证方案回退；恢复数据库前核对备份后新增正式数据，不盲目恢复造成丢失。

### 历史专项合并步骤（须重新授权，不用于普通发布）

1. 明确源仓库提交、本机与 NAS 数据库、目标容器数据卷、维护窗口及未提交资源；未经授权不得开始迁移。
2. 对本机和 NAS 分别生成在线 SQLite 备份，记录上传图片清单与哈希；验证完整性、外键、迁移版本和图片引用。备份失败禁止继续。
3. 在隔离副本执行结构兼容与合并预演，产出新增、相同、NAS 独有和冲突清单；冲突项等待逐项确认，不得执行删除或覆盖。
4. 将代码、静态图片、合并后的数据库候选副本和上传图片上传至独立暂存区并校验；保留服务器私有 `.env`、备份目录和运行数据卷。
5. 正式写入前再次读取 NAS 变更，确认预演仍可幂等合并；使用可回退的事务/临时目录应用已确认的差异，而不是替换整个目标数据库。
6. 重建 `web` 和 `api`，运行统一 Alembic 迁移；不使用未经核验的 `stamp` 绕过结构差异。
7. 验证 ready、完整性、外键、关键记录数量/内容、静态图片、上传图片、敏感路径拒绝及 PDF Logo；验证页面和业务链路。
8. 记录目标、时间、Git 提交、两端备份位置、合并清单、验证结果及失败项；验证失败应按已验证备份回滚，不宣布成功。
