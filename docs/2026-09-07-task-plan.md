## 二、P0：业务链路与数据一致性（先做）

### 1) 询价转报价幂等化（避免重复转成多个报价）
- **现状风险**：后端 `convert-to-quote` 已加查询，但已有 `converted_quote_id` 时直接返回 409，导致重复点击无法复用历史结果。
- **技术方案**：
  - **后端**：
    - `backend/inquiry_repository.py`  
      - 保持 `inquiry_quote_items()` 快照化能力不变。
      - `mark_inquiry_quoted()` 增加“幂等策略”：若已存在 `converted_quote_id`，直接返回该询价快照（可选检查引用 quote 存在且未删除），不再抛 409。
    - `backend/config_routes.py`  
      - `/api/v1/staff/inquiries/{inquiry_id}/convert-to-quote`：若已有转报价，返回 `{"inquiry": {..., "replayed": true}, "quote": ...}`，HTTP 200/201 保持一致。
  - **数据库**：不需要新增表；仅校验引用 quote 是否存在。
  - **验收**：
    - 连续点两次“转报价”，第二次返回同一 `quote.id`，`inquiry.converted_quote_id` 不变。
    - 审计日志仍记录一次转化动作，重复调用返回 `replayed` 标记。

### 2) 报价列表状态过滤与“查询参数化”
- **现状风险**：管理员端报价列表没有按状态过滤入口，无法按需求查看草稿/已发/已归档。
- **技术方案**：
  - **后端**：
    - `backend/quote_repository.py`
      - `list_quotes()` 增加 `status_filter`，支持 `draft|sent|archived|all`，默认 `all`。
      - 返回字段补齐 `lifecycle_status`、`updated_at`、`created_at`，并保持与前端兼容字段。
    - `backend/config_routes.py`
      - `GET /api/v1/quotes` 新增 query：`status=sent`、`include_archived`（admin 可见）、`page/page_size`（有需要可顺便加分页）。
      - 继续保持 customer 与 staff 的权限边界：staff/admin 看全部，customer 只看自己（如已有行为）。
  - **前端**：
    - `admin/admin.js`
      - `loadData()` / `renderQuotes()` 增加过滤器状态位与请求参数拼接。
      - 表头增加/复用状态标签过滤控件（草稿/已发送/已归档）。
  - **验收**：
    - 可单独筛出「仅草稿」「仅已发送」「仅已归档」。
    - 列表排序/分页稳定不变。

### 3) 已归档报价在客户侧可见但不泄露价格（仅记录）
- **现状风险**：目前 `GET /customer/me/quotes` 返回 full quote 详情，归档后希望保留记录但不展示价格与明细。
- **技术方案**：
  - **后端**：
    - `backend/config_routes.py` 的 `customer_own_quotes`、`customer_own_quote`、`customer_own_quote_pdf` 三个接口加入遮蔽层：
      - 当 `lifecycle_status=archived` 时：
        - `items` 置空或最小化；
        - `total_price`、`price`、`item_count` 隐藏或置 0；
        - `pdf` 返回简版提示页或禁发（建议返回“已撤回，查看历史编号”）。
  - **前端**：
    - 用户端“我的报价”列表展示“已撤回（仅历史）”并禁止编辑/导出入口。
  - **验收**：
    - 归档后客户可见记录条目和状态文本，但打不开明细与金额。

### 4) 购物车询价提交与“重复快速点击”幂等
- **现状风险**：`cart/current inquiry` 与 `cart inquiry` 通过 `idempotency_key` 防重，但前端按钮文案、弹窗内容和空状态需收口。
- **技术方案**：
  - **后端**：
    - 保留 `backend/inquiry_repository.py::_insert_inquiry` 的幂等逻辑（已具备），补充快速重复返回的统一消息与 `replayed` 语义。
  - **前端**：
    - `js/cart.js`
      - `openInquiryDialog("cart")`：
        - 禁止未登录和空购物车提交；
        - 按设备/工具/附件汇总显示（已实现）但统一文案格式为“X 台设备 · Y 件工具 · Z 件附件”；
      - `requestSubmit` 期间按钮置灰 + 防抖（300~500ms）；
      - 成功后仅显示一次询价编号与成功态。
  - **验收**：
    - 反复点击不产生重复记录（同 key 仅重放）。
    - 重放返回状态可识别，并提示“已提交/重放成功”。

### 5) 购物车侧栏“购物车中所有内容”统一（去掉选择框/全选依赖）
- **目标**：购物车只支持整单导出/整单分享，不依赖 item checkbox。
- **现状风险**：模板/样式仍保留选择框与勾选相关样式残留。
- **技术方案**：
  - **前端**：
    - `js/cart.js`
      - `renderCartActions()` 保持“导出/分享/关闭”操作可用，但 `share`、`pdf` 固定处理全部 `serverCart`。
      - `remove` 与 `edit` 保留，移除批量多选逻辑。
    - `css/components.css`
      - 隐藏或降级 `.cart-item-select`、`selected` 状态视觉；
      - 侧栏底部操作按钮区按无选择逻辑重排（避免“全选”残留）。
  - **验收**：
    - 无任何 checkbox 影响主流程。
    - 所有导出/分享动作都基于全量 cart。

### 6) 购物车与分享/报价顺序对齐（设备 -> 工具 -> 附件，设备按添加顺序）
- **现状风险**：多个通道显示顺序和导出顺序偶发不一致。
- **技术方案**：
  - **前端**：
    - `js/cart.js`
      - `orderCartItems()` 已有分组排序逻辑，统一复用到 `catalog-cart` 侧栏、summary 与导出 payload。
      - 设备组按 `savedAt`（可回放排序）升序。
      - 工具/附件按 catalog 系统分类排序。
  - **后端**：
    - `backend/commercial` share/export 相关接口保持 server 接收顺序透传，不再二次重排。
  - **验收**：
    - 侧栏显示顺序=导出 PDF 内容顺序=分享内容顺序。

### 7) 后台报价与询价列表操作闭环（转报价/分配/关闭）
- **目标**：把高频操作收口为一套可回放的行为。
- **技术方案**：
  - **后端**：
    - `backend/inquiry_repository.py` / `backend/config_routes.py`
      - 继续保留询价 `status` 流转：`new|assigned|contacted|quoted|closed|cancelled`
      - 支持由 staff/admin 接口赋值、分配、转报价。
  - **前端**：
    - `admin/admin.js`
      - 询价列表增加“状态列 + 分配操作 + 转报价后禁用重复入口（仅提示复用）”。
      - 报价列表保留“编辑/删除/归档/恢复/导出/历史”但与生命周期一致：只有非归档可编辑，已归档仅恢复。
  - **验收**：
    - “已转报价”项无法重复创建新草稿，按钮变为打开已有草稿。
    - 角色权限规则与按钮状态一致。

## 七、今日具体技术方案（实施路线）

### A. 架构约束（统一规范）
- 一切变更优先落在“单一数据源”：
  - 订单/询价/报价的权威状态只来自后端；
  - 前端只做展示重排和文案拼装，不改变业务状态定义。
- 错误与重试策略：
  - 所有重复关键动作统一返回 `idempotent/replayed` 标识；
  - 前端对 409/409-like 场景做“结果复用”而非直接失败。
- 字段兼容：
  - 历史前端消费字段保留，新增字段采用可选字段，避免旧代码读不到报错。

### B. 购物车核心链路改造（优先级 P0）
1. **重复转报价与重复询价防御**
   - 接口：`POST /api/v1/staff/inquiries/{id}/convert-to-quote`
   - 修改点：
     - `backend/inquiry_repository.py`：`mark_inquiry_quoted` 返回已有 `converted_quote_id` 时返回已有 quote（不抛 409）。
     - `backend/config_routes.py`：转换成功返回中带 `replayed` 标识；HTTP code 仍保持可识别成功语义（建议 200/201）。
   - 验收点：
     - 连点两次只生成一条报价；`quote.id` 恒定。

2. **归档报价客户端可见性控制**
   - 接口：
     - `GET /api/v1/customer/me/quotes`
     - `GET /api/v1/customer/me/quotes/{id}`
     - `GET /api/v1/customer/me/quotes/{id}/pdf`
   - 修改点：
     - 当 `lifecycle_status = archived` 时，剥离 `items/price/total`；
     - PDF 入口返回归档提示页或历史摘要，不返回敏感金额明细。
   - 验收点：
     - 客户端仅看到状态与时间，不再看到金额与明细。

3. **报价列表状态化**
   - 接口：`GET /api/v1/quotes`
   - 修改点：
     - `backend/quote_repository.py` 支持 `status_filter` 与 `include_archived`；
     - `backend/config_routes.py` 透传参数并限定 staff/admin 可见范围。
   - 验收点：
     - 可独立查看草稿/已发/已归档/全部。

### C. 前端一致性工程（优先级 P1）
1. **购物车操作统一**
   - 文件：`index.html`、`js/cart.js`、`css/components.css`
   - 修改点：
     - 顶部按钮：`导出PDF / 分享 / 关闭` 顺序固定；
     - 移动端保持按钮图标化、桌面端文案清晰；
     - “详情/编辑/删除”按钮统一命名与翻译映射。
   - 风险：
     - 小屏时按钮组宽度不足 → 可先改为图标+`aria-label`。

2. **分享/报价/询价详情展示统一**
   - 文件：`admin/admin.js`
   - 修改点：
     - 详情模块统一 `设备X台 / 工具Y件 / 附件Z件`；
     - 去除重复标题与冗余 `h4`；
     - 数量显示右对齐。
   - 风险：
     - 历史数据字段为空时需回退展示 `-`。

3. **顺序与展示统一**
   - 文件：`js/cart.js`
   - 修改点：

## 十二、分享、询价与报价协作改造（已确认，执行中）

### 12.1 目标与业务规则

1. 管理员和所有启用的业务员都可以查看全部分享记录和全部询价记录。
2. 一条分享或询价允许不同业务员分别生成报价；报价归属于创建它的业务员。
3. 业务员只能查看、编辑、导出、发送和管理自己的报价；管理员可以查看和管理所有报价。
4. 分享和询价列表实时派生报价状态，不在分享或询价表中复制易失真的“已报价”字段。
5. 已经存在报价时，普通“报价”操作必须二次确认；已有本人报价时优先提供“查看我的报价”快捷入口。
6. 询价 PDF 与分享 PDF 一样属于配置/需求文件，不显示价格；只有正式报价 PDF 显示价格。

### 12.2 当前实现审查

#### 已具备

- `commerce_quotes.source_share_id` 和 `commerce_quotes.source_inquiry_id` 可以表达一条来源对应多份报价。
- 报价保存已有版本号乐观锁；发送已有幂等键。
- `/api/v1/quotes` 已实现业务员仅查询本人报价、管理员查询全部报价。
- 分享记录 `/staff/shares` 已对管理员和业务员开放全部数据。
- 分享、询价和报价已统一使用“设备 → 工具 → 附件”聚合顺序。

#### 当前缺口

- 业务员询价查询仍使用“未分配或分配给自己”的范围限制，不能查看全部询价。
- `customer_inquiries.converted_quote_id` 只能记录一份报价；转换接口遇到已有报价会直接复用，不能支持多业务员报价。
- 分享列表接口没有返回关联报价数量、报价业务员和本人报价 ID。
- 询价列表只返回当前负责人名称，不返回所有报价业务员及本人报价。
- 分享和询价列表没有一致的“已报价/未报价”展示与重复报价确认。
- 询价记录没有 PDF 导出接口，也没有“更多”操作菜单。
- 报价编辑器只有数量、单价输入，缺少添加、删除及设备内配置维护能力。
- 报价项目是松散的 `items_json` 行，缺少稳定的行 ID 和设备父级关系，复杂编辑容易串组。

### 12.3 数据模型技术路线

#### P0-1 报价来源保持一对多

- 继续以 `commerce_quotes.source_share_id`、`source_inquiry_id` 为真实关联，不新增重复关联表。
- `customer_inquiries.converted_quote_id` 暂时保留用于兼容历史数据，但降级为“首份/旧版关联报价”，不再作为是否允许创建报价的唯一判断。
- 增加索引：
  - `commerce_quotes(source_share_id, user_id, updated_at)`；
  - `commerce_quotes(source_inquiry_id, user_id, updated_at)`。
- 列表查询按来源聚合非归档报价，返回：
  - `quote_count`：有效关联报价总数；
  - `quoted_by`：去重后的业务员 `{id, display_name}`；
  - `own_quote_count`：当前业务员自己的报价数；
  - `own_latest_quote_id`：本人最近一份可访问报价；
  - `latest_quote_at`：最近报价时间。
- 已归档报价是否计入“已报价”：默认不计入当前状态，但历史抽屉中仍可查询。

#### P0-2 报价明细结构升级

- 报价 `items_json` 升级为兼容式 schema，不拆旧表：
  - `line_id`：稳定行 ID；
  - `kind`：`product/option/surcharge/tool/accessory`；
  - `source_id`：设备或目录项目 ID；
  - `parent_device_key`：设备配置行所属设备；
  - `device_sequence`：设备序号；
  - `category_id/category_sort_order/sort_order`：配置归组和排序；
  - `availability`：`active/inactive/missing/snapshot_only`；
  - `quantity/price/price_cny/price_usd`。
- 读取旧报价时动态补齐 `line_id` 和父级关系；只有再次保存时写入新结构，不批量覆盖历史报价。
- 服务端始终重新校验数量、单价、父级关系和总价，前端传入的总价只作展示参考。

### 12.10 执行前冻结规则（评审补充）

以下规则优先于 12.1 至 12.9 中可能存在歧义的描述，实施时不得自行改变。

#### A. 每名业务员每个来源最多一份有效报价

- 同一分享或询价允许不同业务员分别创建自己的报价。
- 同一业务员针对同一来源只能存在一份未归档报价。
- 本人已有有效报价时，“查看我的报价”直接打开该报价。
- 再次点击“报价”必须弹窗说明已有本人报价，并确认是否继续编辑；不得直接创建重复草稿。
- 本人原报价归档后才允许为同一来源创建新报价；恢复归档报价前必须检查是否已有新的有效报价。
- 数据库与仓储层共同保证唯一性，不能只依赖按钮禁用。

建议唯一约束逻辑：

- 分享来源：`source_share_id + user_id + lifecycle_status != archived`；
- 询价来源：`source_inquiry_id + user_id + lifecycle_status != archived`；
- 直接创建的报价不受来源唯一约束。

#### B. 新旧分享来源兼容

- 现有 `source_share_id` 外键只能稳定指向新版 `commerce_shares`，不能假设旧版 `config_shares` 一定可关联。
- 报价来源增加兼容字段：`source_type`、`source_document_version`、`source_document_id`、`source_code`。
- 新字段作为统一反查依据；原 `source_share_id`、`source_inquiry_id` 保留，供新版数据使用和外键校验。
- 历史报价读取时动态映射旧字段，不批量改写原始报价。

#### C. 询价负责人和报价业务员分离

- `assigned_to` 只代表询价负责人，不代表唯一可报价人员。
- 所有业务员可以读取全部询价并基于询价创建自己的报价。
- 接手、联系、关闭和调整询价状态仍由负责人或管理员执行。
- 列表分别显示负责人、报价业务员和报价数量。
- 不允许使用某一份报价的创建人覆盖询价负责人。

#### D. “已报价”统计口径

- 草稿和已发送但未归档的报价计入“已报价”。
- 已归档报价不计入当前有效报价数量，但显示“有历史报价”。
- 已删除报价不计入数量，只保留审计记录。
- 已撤回客户投递但报价本身未归档时，仍计入已有报价，并显示“已撤回”。
- 第一份有效报价生成时记录 `first_quoted_at`；后续其他业务员报价只更新 `latest_quoted_at`，不得覆盖负责人或首次报价时间。

#### E. 参考价与实际报价分离

报价行分别保存 `reference_price`、`quoted_price`、`price_overridden`、`currency` 和 `quantity`。

- 新加入工具、附件和配置时，用参考价初始化实际报价。
- 自动填价只更新尚未人工修改的项目。
- 目录参考价后续变化不覆盖历史报价和人工价格。
- 服务端使用 `quoted_price × quantity` 计算总价，不接受前端伪造总价。

#### F. 设备配置编辑边界

- 设备基础行不可删除。
- 电机和通道属于基础价格因素，修改后重新计算建议基础价。
- 电源作为增加费用选项单独显示。
- 普通可选配置允许添加和删除。
- 电机、通道和电源不得混入普通可选配置选择器。
- 设备型号及设备序号保持稳定；不同设备的配置不能互相移动。

#### G. 历史快照和失效项目

- 报价编辑器同时读取来源快照、当前目录状态和报价明细，不能仅依赖当前目录重建。
- 已停用或已删除项目继续显示快照编号、名称、数量和已保存价格。
- 失效项目标记为“已失效”或“仅历史快照”，允许保留或删除，但不能作为新项目再次添加。
- 某一项目失效不得阻止整份分享、询价或报价打开。

#### H. 报价修订版本

- 普通保存只更新草稿和乐观锁 `version`。
- 发送给客户时生成不可变 `quote_revision`。
- 已发送报价再次编辑时创建新的可编辑状态，不修改客户已经收到的修订快照。
- 再次发送生成新的不可变修订，客户查看对应最新有效版本。
- 不在每次输入或未发送的普通保存时创建冗余历史版本。

#### I. 聚合查询与性能

- 分享和询价分页列表必须通过一次聚合查询返回报价摘要，禁止每行单独查询报价。
- 增加来源、创建人、生命周期和更新时间组合索引。
- 聚合字段至少包含：有效报价数量、历史报价数量、报价业务员、本人报价 ID、最近报价时间。
- 姓名聚合在服务端完成去重，前端只负责截断展示和完整名单弹层。

#### J. 询价 PDF 数据边界

- 管理员和业务员都可以导出任意可读取询价的 PDF。
- PDF 使用询价创建时的客户与配置快照，不受账号资料或目录后续修改影响。
- PDF 显示询价编号、客户、联系方式、创建时间、状态、补充说明及全部配置内容。
- PDF 不显示参考价、报价单价、总价、内部负责人、内部处理备注或其他业务员报价情况。

#### K. 跳转与异常恢复

- 报价已归档：打开只读详情并提供符合权限的恢复入口。
- 报价已删除：刷新来源记录并移除失效关联按钮。
- 报价版本已更新：加载最新版本并提示内容已刷新。
- 当前账号角色变化、停用或无权访问：拒绝打开并返回报价列表。
- 网络暂时失败：保留当前列表状态并提供重试，不清空筛选条件。
