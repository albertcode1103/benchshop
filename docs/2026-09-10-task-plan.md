## 二、审查发现的问题

### P0：Web 镜像公开了内部源资料

- `deploy/Dockerfile.web` 当前执行 `COPY tb /usr/share/nginx/html/tb`，会把 `tb/` 内所有文件作为公开静态资源发布。
- 当前目录包含 `.xlsx`、`.xls`、`.psd`、`.zip` 和资料 PDF；`.dockerignore` 尚未排除这些扩展名。
- 已实测 Albert-NAS 上 `/tb/pricelist.xlsx` 和 `/tb/HarmonyOS+Sans.zip` 返回 HTTP 200。价格源表、设计源文件和字体压缩包存在未授权下载风险，同时显著放大镜像体积。

修复计划：

- [ ] 建立 Web 静态资源白名单，只发布页面实际引用的 HTML、CSS、JavaScript、字体及 PNG/JPG/JPEG/WebP/SVG。
- [ ] 在 `.dockerignore` 排除 `tb/**/*.xlsx`、`tb/**/*.xls`、`tb/**/*.psd`、`tb/**/*.zip`、源资料 PDF 和临时文件。
- [ ] 调整 Web 镜像复制方式，避免以后新增源文件时被自动公开。
- [ ] 在 Nginx 增加敏感扩展名拒绝规则作为第二道防线。
- [ ] 构建镜像后逐项请求敏感路径，确认均为 404/403；同时确认 133 张现有静态产品图片全部可读。
- [ ] 重建 Albert-NAS Web 容器，验证旧镜像中的源资料已不可访问；不删除本机原始资料。

验收标准：页面和产品图片显示不变；Excel、PSD、ZIP、源 PDF 无法通过网站下载；镜像中不存在这些文件。

### P0：数据库初始化与 Alembic 迁移状态可能漂移

- Docker 入口会执行 `alembic upgrade head`，但本机直接启动仅调用 `initialize_database()`；后者自行补字段却不更新 `alembic_version`。
- 本轮部署前已实际出现“字段可用，但版本仍停在 `0018`，代码迁移头为 `0025`”的状态。这会让本机、测试和 NAS 在升级时走不同路径，增加重复迁移及环境不一致风险。

修复计划：

- [ ] 将本机、测试和 Docker 的数据库升级统一到同一 Alembic 入口。
- [ ] `initialize_database()` 只保留连接与必要的兼容保护，不再成为第二套独立迁移系统。
- [ ] 启动时校验迁移头；版本落后时明确升级或拒绝进入业务服务，禁止静默漂移。
- [ ] 覆盖空数据库、`0018` 历史数据库、字段已存在但版本滞后的数据库三种升级样例。
- [ ] 每次迁移前继续创建 SQLite 在线备份，升级后执行 `foreign_key_check`、`integrity_check` 和关键表数量核对。

验收标准：所有环境启动后均显示 `20260909_0025 (head)`；重复启动不产生结构变化或数据丢失。

### P1：请求体和嵌套业务数据缺少统一边界

- `SaveConfigRequest.selections`、`QuoteRequest.items`、部分旧目录模型使用宽泛的 `dict/list`，未统一限制项目数、键数量、嵌套深度和文本长度。
- 报价归一化会保留客户端提交的额外字段；虽然金额会由服务端重算，但异常大快照可能进入数据库、PDF 和前端渲染链路。
- `_enforce_catalog_request_size()` 只检查 `Content-Length`，且在 FastAPI 已解析请求模型后执行；缺少该请求头或使用分块传输时无法形成可靠的内存保护。

修复计划：

- [ ] 为配置、购物车、分享、询价和报价建立显式 Pydantic 行模型，拒绝未知字段。
- [ ] 限制批量条目数、配置选项数、文本长度、JSON 嵌套深度及单请求总大小。
- [ ] 报价入库只保留渲染和审计需要的白名单字段，金额仍由服务端重新计算。
- [ ] 在 ASGI/Nginx 两层实施一致的请求体限制，并覆盖无 `Content-Length` 与分块请求。
- [ ] 超限统一返回 413/422，不写数据库、不生成半成品文件。

验收标准：正常购物车、分享、询价和报价行为不变；超大或畸形载荷被快速拒绝，数据库记录数不变化。

### P1：Excel 导入存在压缩包膨胀和超大 XML 风险

- 上传文件本身限制为 10 MB，但 `parse_xlsx()` 会直接解压并读取共享字符串和工作表 XML。
- 尚未限制 ZIP 条目数、单条目解压大小、总解压大小、压缩比、最大行列数和单元格长度；恶意或异常工作簿可能耗尽内存或长时间占用服务。

修复计划：

- [ ] 解压前检查 ZIP 条目白名单、条目数、压缩比、单项与累计解压大小。
- [ ] 限制工作表数量、最大行列数和单元格文本长度。
- [ ] 预览和正式提交复用完全相同的解析及校验逻辑。
- [ ] 保留“提交前自动备份 + 单事务回滚”，并补充压缩炸弹、截断 XML、重复行和超长单元格测试。

验收标准：合法现有模板导入结果不变；异常文件在写库前被拒绝，API 仍可继续响应其他请求。

### P1：旧目录写入接口存在并发覆盖与规则分叉

- 管理端仍调用部分旧 `/api/v1/admin/products/*` 和 `/config-catalog/*` 写入接口。
- 新目录编辑器已具备版本号冲突检测、图片引用校验和较完整的数据规范；部分旧接口没有版本字段或相同的字段长度、图片路径及聚合编号校验。
- 两个管理员或业务员同时编辑时，旧接口可能以后保存者覆盖先保存者；同一业务数据经不同接口写入时可能得到不同结果。

修复计划：

- [ ] 保留现有 URL 和界面，旧接口内部转交统一目录服务，不再维护两套规则。
- [ ] 为仍在使用的旧保存流程补充版本校验和 409 冲突响应；前端沿用现有弹窗，仅增加冲突提示和重新载入。
- [ ] 统一编号规范、名称清洗、图片引用、价格边界、排序和审计字段。
- [ ] 添加双会话并发保存、失败回滚、图片引用保持和旧客户端兼容测试。

验收标准：单人操作体验与布局不变；并发修改不会静默覆盖；同一数据从新旧入口保存结果一致。

### P1：健康检查不能覆盖真实数据链路

- `/api/v1/health` 当前固定返回 `{"status":"ok"}`，只证明 API 进程能够响应。
- 本轮 Albert-NAS 曾出现健康接口为 200，但前端因 API 地址判断错误而整页无产品数据的情况。

修复计划：

- [ ] 保留现有轻量存活检查，新增数据库就绪检查，验证连接、迁移版本和只读查询。
- [ ] 部署验收增加同源 `/api/v1/products`、主页关键静态资源及至少一张产品图片的冒烟检查。
- [ ] Compose 健康检查改用就绪端点；Web 重建后自动检查首页资源版本号。
- [ ] 失败时输出可定位的检查项，不返回客户数据或内部路径。

验收标准：数据库不可读、迁移落后、API 代理错误或关键静态资源缺失时，部署验收能够明确失败。

### P1：登录限流状态缺少容量回收保护

- 当前限流器为进程内 `defaultdict(deque)`；登录键包含客户端提交的账号标识。
- 登录标识没有在请求模型层设置明确最大长度，持续使用不同标识可积累限流键；多进程部署时各进程限流状态也不共享。

修复计划：

- [ ] 限制登录标识和所有密码字段长度，进入 PBKDF2 前先完成轻量校验。
- [ ] 为限流键增加定期淘汰和最大容量，避免无界增长。
- [ ] 明确当前单进程部署约束；未来启用多 Worker 时切换共享限流存储。
- [ ] 增加多账号喷洒、超长标识和限流恢复测试。

验收标准：正常登录与错误提示不变；异常请求不会导致限流内存持续增长，也不能绕过既有限制。

### P2：敏感响应缓存与浏览器安全策略可继续收紧

- 账户资料、询价、报价和授权 PDF 未统一声明 `Cache-Control: no-store`。
- Nginx 已有 `X-Content-Type-Options`、`X-Frame-Options`、`Referrer-Policy` 和 `Permissions-Policy`，但尚无经过兼容验证的 CSP。
- 目录图片路径允许非上传目录路径，需要明确限制为可信站内路径或 HTTP(S) 图片，避免异常协议和不可控资源引用。

修复计划：

- [ ] 给账户、客户业务中心、后台数据和授权 PDF 响应增加 `Cache-Control: no-store`。
- [ ] 以报告模式验证 CSP，再收紧脚本、样式、图片和连接来源；不得破坏当前内联 SVG、图片和弹窗。
- [ ] 图片地址仅允许项目静态路径、受控上传路径及明确允许的 HTTP(S) 地址，拒绝其他协议。
- [ ] 生产 CORS 配置缺失或仍为示例值时启动失败；本机开发规则保持可用。

验收标准：现有页面视觉和操作无变化；敏感响应不被缓存；异常资源协议被拒绝。

### P2：依赖供应链检查尚未固化

- `pip check` 当前通过，但 requirements 使用版本范围而非锁定解析结果。
- 本机测试环境仍为 Python 3.8，已收到加密依赖停止支持警告；生产镜像使用 Python 3.12。
- 未配置可重复执行的 CVE 扫描和镜像软件包扫描。

修复计划：

- [ ] 在 Python 3.12 环境生成并保存可复现的依赖锁定结果，不直接进行大版本升级。
- [ ] 将 `pip-audit` 或等价工具加入开发检查，并为高危漏洞设定失败门槛。
- [ ] 对 Docker 镜像增加只读 CVE 扫描记录，升级前后运行完整回归。
- [ ] 本机测试逐步切换到 Python 3.12，与生产运行时保持一致。

验收标准：依赖版本可复现；已知高危漏洞有明确处理结果；升级不改变现有业务行为。
