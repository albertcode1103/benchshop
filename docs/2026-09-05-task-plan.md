## 二、已确认的设计方向

1. 已发送报价修改后，必须再次执行“发送更新”，客户才能看到新版内容。
2. 报价默认有效期暂定为 30 天，实施前由用户最终确认。
3. 已撤回报价在客户侧保留编号、标题和撤回时间，但隐藏价格、明细和 PDF。
4. 客户授权一律依据稳定的 `recipient_user_id`，不得通过邮箱、手机号或分享码推断权限。
5. 正式报价允许客户查看价格；普通配置页面、普通分享和用户配置 PDF 继续隐藏价格。

## 三、P0：报价数据安全与生命周期

### 3.1 扩展新版报价表

为 `commerce_quotes` 增加：

- `quote_number`：正式报价编号，例如 `BTQ-20260905-0001`。
- `lifecycle_status`：`draft`、`sent`、`archived`。
- `version`：乐观锁版本，避免多人编辑覆盖。
- `valid_until`：报价有效期。
- `payment_terms`：付款条件。
- `delivery_terms`：交付周期。
- `tax_note`：税费说明。
- `freight_note`：运费说明。
- `sales_contact`：业务员联系方式快照。
- `quote_note`：报价备注。
- `archived_at`、`archived_by`：归档记录。

报价编号必须由服务端在数据库事务中生成，浏览器不得自行编号。

### 3.2 新增不可变报价版本

新增 `quote_revisions`：

```text

revision_number
snapshot_json
created_by
created_at
```

每次正式发送或发送更新时生成完整快照，包括客户、业务员、来源分享、币种、项目、数量、单价、小计、总价、有效期、商务条款和语言。客户详情与 PDF 只读取已发送 revision，不读取业务员仍在编辑的工作稿。

### 3.3 扩展报价投递记录

为 `quote_deliveries` 增加：

- `revision_id`：客户当前收到的正式版本。
- `last_viewed_revision_id`：客户最后查看的版本。
- `notification_state`：站内提醒处理状态。

同一报价重新发送时不新增重复投递关系，而是更新 revision、清空查看时间并重新标记未读。

### 3.4 删除与归档规则

- 未发送草稿允许确认后永久删除。
- 已发送报价禁止永久删除，只允许撤回或归档。
- 归档报价后台可恢复。
- 撤回后客户保留基础记录，但不能打开价格明细或下载 PDF。
- 删除、撤回、归档、恢复和重新发送全部写入审计日志。

### 3.5 数据迁移

- 新迁移建议使用 `20260905_0017`。
- 执行迁移前生成并验证 SQLite 在线备份。

## 四、P0：服务端接口与事务

### 4.1 员工报价接口

```text
GET    /api/v1/staff/quotes
GET    /api/v1/staff/quotes/{quote_id}
PATCH  /api/v1/staff/quotes/{quote_id}
POST   /api/v1/staff/quotes/{quote_id}/deliver
POST   /api/v1/staff/quotes/{quote_id}/withdraw
POST   /api/v1/staff/quotes/{quote_id}/archive
POST   /api/v1/staff/quotes/{quote_id}/restore
GET    /api/v1/staff/quotes/{quote_id}/deliveries
GET    /api/v1/staff/quotes/{quote_id}/revisions
```

发送报价必须在单个数据库事务中完成：

1. 验证报价归属及业务员权限。
2. 验证客户账号有效且未归档。
3. 验证来源分享与客户关系。
4. 检查项目、数量、单价和总价。
5. 创建不可变 revision。
6. 创建或更新 delivery。
7. 更新报价状态。
8. 写入审计日志。
9. 返回投递结果和最新版本。

任一步失败必须整体回滚；重复点击采用幂等处理。

### 4.2 客户报价接口

```text
GET  /api/v1/customer/me/quotes
GET  /api/v1/customer/me/quotes/unread-count
GET  /api/v1/customer/me/quotes/{quote_id}
GET  /api/v1/customer/me/quotes/{quote_id}/pdf
POST /api/v1/customer/me/quotes/{quote_id}/acknowledge
```

- 客户只能读取投递给自己账号的 revision。
- PDF 下载执行相同的接收人权限校验。
- 已撤回报价不得返回价格和项目明细。
- 客户打开报价后更新 `last_viewed_revision_id` 和查看时间。

## 十二、2026-09-05 新增调整：分享、询价、报价分流

### 12.1 业务定义

三个对象必须明确分离：

| 对象 | 用户意图 | 是否通知销售 | 是否包含价格 | 后续动作 |
|---|---|---:|---:|---|
| 分享 | 把当前配置交给其他人查看或加入购物车 | 否 | 客户侧不显示；后台保留参考价快照 | 业务员主动检索后仍可人工转报价 |
| 询价 | 客户明确要求销售联系并提供报价 | 是，生成后台待处理记录 | 客户提交时不显示价格 | 分配业务员、联系客户、转为报价草稿 |
| 报价 | 业务员填写并正式发送的商业文件 | 是 | 是 | 发送、更新、撤回、归档和 PDF |

用户执行“分享”时不得自动创建询价、不得改变询价状态、不得向业务员制造待处理任务。后台分享记录仍保留“转为报价”入口，但这属于业务员主动处理，不表示客户曾经询价。

新增 `customer_inquiry_items`：

```text

```

设计约束：

- 询价必须绑定稳定的 `created_by` 用户 ID，不通过邮箱或手机号推断归属。
- 联系资料同时保存快照，避免客户之后修改资料导致历史询价失真。
- 询价项目采用不可变快照，目录项目之后被删除或停用也不影响后台查看原始需求。
- `idempotency_key` 与 `created_by` 建立唯一约束，避免慢网络或重复点击生成多条询价。
- 询价不依赖分享码，不自动创建 `commerce_shares`。
- 转报价后保留询价原始快照，报价项目是独立工作稿，不反向修改询价。
- 同一询价重复执行“转为报价”时默认打开已有报价草稿，不重复创建报价。

### 12.3 P0：两个询价入口

#### 当前设备选配入口

位于主页“设备当前选配”区域：

1. 校验用户已登录；未登录时按钮保持可见，点击后打开登录流程并记录待恢复动作，不能直接提交询价。
2. 校验设备、颜色以及必选的电机、电源、通道等规则。
3. 服务端根据 `product_id + color + selections` 分别生成中英文快照。
4. 不强制保存到购物车，也不修改已有购物车。
5. 弹出提交确认卡片，显示当前设备摘要、账号联系方式和可选留言。
6. 用户确认后生成 `source_type=current_device` 的询价记录并返回询价编号。

#### 购物车入口

位于购物车底部：

1. 必须登录后才能真正提交；未登录时按钮保持可见并引导登录，登录成功后恢复询价确认流程。
2. 服务端直接读取该用户全部有效购物车内容，不接受浏览器自行声明部分项目。
3. 空购物车禁止提交并给出明确提示。
4. 按“设备、工具、附件”的既定顺序生成快照。
5. 支持仅设备、仅工具、仅附件以及混合购物车。
6. 用户确认后生成 `source_type=cart` 的询价记录并返回询价编号。

两个入口都不应在单击按钮后立即静默创建记录。按钮先打开统一确认卡片，最终“提交询价”才产生业务记录，避免误触和重复询价。登录成功后只恢复到确认卡片，不自动发送，用户仍需最后确认。

权限与状态规则：

- “全选”控件。
- `selectedCartIds` 及仅针对勾选项的操作状态。
- 底部“分享所选、导出 PDF、删除所选”操作组。

购物车标题栏调整为：


- “分享”默认分享购物车全部有效内容。
- “导出 PDF”默认导出购物车全部有效内容。
- 购物车为空或正在加载时两个按钮禁用。
- 桌面端显示图标和文字；窄屏可只显示图标，但必须保留 `aria-label`、可见焦点和触摸提示。
- 分享和导出继续使用当前整车排序规则，不改变价格隔离策略。

购物车底部只保留一个主按钮：

```text
联系销售获取报价 / Contact Sales for a Quote
```

- 按钮对应“购物车询价”，不是分享，也不是立即生成报价。
- 未登录不能提交；入口仍可点击并触发登录。登录完成后恢复原待办动作和购物车状态，但不自动提交。

### 12.6 P1：购物车卡片操作


删除规则：

- 删除“维修工具”聚合卡片表示移除购物车中的全部维修工具。
- 删除“设备附件”聚合卡片表示移除购物车中的全部附件。
- 工具和附件单项仍可在“修改”窗口中调整数量或逐项移除。

- 聚合删除确认内容必须显示项目种类、不同项目数和总件数。
- 服务端批量删除必须在一个事务中执行；任一项目版本冲突时整体失败并刷新购物车，禁止部分删除。

### 12.10 分优先级执行技术方案

以下顺序同时考虑数据安全、现有链路兼容、可独立验收和回滚难度。正式实施前不修改生产数据，不同步 NAS。

#### P0-A：冻结业务契约与建立回归基线

目标：先证明旧功能现状，再开始结构调整，避免把历史问题误认为本次改动引入。

技术要点：

1. 对本地 SQLite 执行一致性检查并生成带时间戳备份，记录数据库迁移版本、数据量和文件哈希。
2. 固定三条业务规则：分享不创建询价；询价不直接创建正式报价；只有已发送报价对客户可见。
3. 为当前购物车分享、购物车 PDF、分享查询、报价保存与发送建立接口契约快照。
4. 记录旧版 `config_shares` 与新版 `commerce_shares` 的兼容用例，不迁移或删除历史记录。
5. 建立失败基线：未登录、空购物车、项目失效、重复点击、权限不足、版本冲突和 PDF 失败。

验收门槛：现有分享、导出、报价测试全部通过；数据库备份能够在临时文件中恢复并通过维护检查。

#### P0-B：先完成报价不可变版本 `20260905_0017`

目标：询价转报价前先解决“已发送报价会被工作稿修改”的数据风险。

技术要点：

1. 新增 `quote_revisions`，正式发送时保存客户、业务员、来源、币种、项目、金额、条款和语言完整快照。
2. `quote_deliveries` 绑定 `revision_id`，客户详情和 PDF 只读取已发送 revision。
3. 已发送报价禁止硬删除；采用撤回和归档。
4. 保存草稿、生成 revision、投递客户和审计写入必须明确事务边界。
5. 保留旧报价只读兼容，不按邮箱或手机号自动绑定客户。

验收门槛：业务员修改工作稿但未重新发送时，客户看到的正文和 PDF 保持不变。

#### P0-C：新增询价迁移 `20260905_0018`

目标：建立与分享、报价独立的询价数据链路。

技术要点：

1. 创建 `customer_inquiries` 与 `customer_inquiry_items`，添加外键、状态约束、索引和唯一幂等约束。
2. 询价编号由服务端在事务中生成，建议格式 `BTI-YYYYMMDD-序号`，浏览器不得自行编号。
3. `snapshot_json` 保存中英文历史内容；价格可保留为后台参考快照，但客户接口必须经过 `without_prices` 清理。
4. `converted_quote_id` 指向新版报价；同一询价仅允许一个当前有效报价草稿。
5. 状态变更采用 `version` 乐观锁，防止管理员和业务员同时覆盖。
6. 迁移 `downgrade` 不删除业务记录，回退使用已验证备份。

验收门槛：迁移可重复检查、历史数据不变、旧分享和旧报价读取正常。

#### P0-D：抽取统一快照服务与实现询价领域逻辑

目标：分享、购物车 PDF 和询价复用同一套项目加载、排序与中英文快照规则，但保持不同业务语义。

建议代码边界：

```text
backend/commerce_document_service.py   加载、校验、排序并生成中英文项目快照
backend/inquiry_repository.py          询价事务、状态、分配、转换与查询
backend/inquiry_routes.py              客户和员工接口、权限及错误映射
backend/customer_payload.py            继续负责客户价格字段隔离
```

技术要点：

1. 从 `commerce_repository.py` 抽取纯粹的文档构建能力，分享仍写入分享表，询价仍写入询价表，禁止一个入口隐式创建另一个对象。
2. “当前设备选配”由服务端分别构建中英文快照，不信任浏览器传来的名称、价格或描述。
3. “整个购物车询价”由服务端读取用户当前全部有效购物车，不接收部分项目 ID。
4. 询价创建、项目写入、幂等记录和审计日志放在同一事务。
5. 转报价时复制询价快照到报价工作稿；失效项目加风险标记，不自动丢弃。
6. 重复转报价返回已有草稿及稳定结果，不产生重复报价。

验收门槛：仅设备、仅工具、仅附件和混合购物车均能询价；分享数量不因询价而变化。

#### P1-A：实现登录后恢复动作

目标：采用已确认方案，让未登录用户知道入口用途，同时保证任何询价都经过认证和最终确认。

技术要点：

1. 在 `js/auth.js` 增加内存级 `pendingAuthenticatedAction`，只保存动作类型与必要的非敏感定位信息。
2. 未登录点击询价入口时设置待办动作并打开登录窗口。
3. 登录成功事件统一派发 `boten:auth-changed`，由询价模块消费一次待办动作。
4. 恢复时重新从当前页面状态或服务器购物车读取内容，不能沿用登录前可能已经变化的旧快照。
5. 登录成功后只打开询价确认卡片，不自动调用创建接口。
6. 用户关闭登录窗口、切换注册、登录失败或主动退出时清除待办动作。
7. 页面刷新后不恢复待办动作，避免意外弹窗或迟到提交。

验收门槛：登录失败后可以再次登录；成功后回到正确入口；无论何种情况都不会自动生成询价。

#### P1-B：购物车全量操作重构

目标：删除选择态，分享和 PDF始终处理完整购物车。

建议修改范围：

```text
index.html
js/cart.js
js/language.js
css/components.css
```

技术要点：

1. 删除 `selectedCartIds`、全选控件、卡片选择框及相关事件绑定。
2. 增加 `allCartItems()`，以当前 `serverCart` 为唯一界面来源；提交前服务端再次验证所有权和有效状态。
3. 标题栏按钮在加载和空购物车时禁用，并避免重复点击。
4. 手机端仅隐藏文字，不隐藏按钮语义；图标按钮至少 40×40px并提供 `aria-label`。
5. 分享成功仍显示分享码；导出 PDF 失败不得改变购物车。
6. 删除操作与分享、导出解耦，不再保留批量选择删除入口。

验收门槛：页面不存在选择态残留；分享、PDF、购物车显示顺序完全一致。

#### P1-C：卡片删除与并发控制

目标：为每类卡片提供明确、安全、可恢复的删除反馈。

技术要点：

1. 设备卡片使用现有单项归档接口并携带版本号。
2. 工具和附件聚合删除新增按类型归档接口，服务端在单事务中验证全部项目版本后统一归档。
3. 确认弹窗显示删除对象和数量，默认焦点落在“取消”，危险按钮使用统一红色样式。
4. 发生 `409` 冲突时不做部分删除，关闭加载态、重新抓取购物车并提示内容已变化。
5. 删除成功后保持购物车滚动位置并把焦点移动到相邻卡片或购物车标题。

验收门槛：单设备、整组工具、整组附件和编辑窗口单项删除均正确；无原生浏览器确认框。

#### P1-D：两个询价确认界面

目标：让用户在提交前明确知道发送给销售的内容和联系方式。

技术要点：

1. 复用网站对话框规范，标题、内容区和底部操作分层，中央内容独立滚动。
2. 当前设备入口展示型号、颜色、电机、电源、通道和选配数量。
3. 购物车入口按设备、维修工具、设备附件聚合展示数量摘要。
4. 联系方式从登录账号读取；允许在确认卡片中跳转个人中心修改，但不能临时写入未验证的邮箱或手机号。
5. 提供可选询价留言，限制长度并在服务端再次校验。
6. 成功后显示询价编号、提交时间和“等待销售联系”，并禁止重复提交按钮。
7. 中英文内容使用明确词义：`Inquiry` 表示询价，`Quotation` 仅表示正式报价。

验收门槛：390px、1024px、桌面端及 200% 缩放下可完整查看和操作；键盘焦点不会离开弹窗。

#### P1-E：后台询价管理与转报价

目标：让明确询价形成可追踪待办，而不是依赖业务员轮询分享记录。

建议修改范围：

```text
admin/index.html
admin/admin.js
admin/admin.css
backend/inquiry_routes.py
backend/inquiry_repository.py
```

技术要点：

1. 新增独立导航和 URL 状态，例如 `#inquiries`，刷新和返回键可恢复。
2. 列表服务端分页、模糊搜索和状态筛选；不在浏览器一次加载全部记录。
3. 详情使用右侧抽屉，设备、工具、附件单列聚合，底部固定“领取/分配、标记已联系、转为报价”。
4. 业务员领取采用条件更新：只有 `assigned_to IS NULL` 或仍属于本人时成功。
5. 转报价调用独立接口，不在前端拼接数据库关系；服务端返回已有或新建报价草稿。
6. 报价接收客户固定为询价 `created_by`，如需改接收人必须由管理员执行并写审计。
7. 已转报价后从询价详情进入关联报价，不重复展示“新建报价”。

验收门槛：两名业务员同时领取只有一人成功；重复转报价不产生重复记录；客户只有收到正式 revision 后才能看到报价。

#### P2：个人中心、通知和运营状态

目标：补齐客户与业务员的后续追踪，但不阻塞第一版询价主链路。

技术要点：

1. 个人中心增加“我的询价”，显示编号、来源、状态、提交时间和关联报价。
2. 新询价为后台增加未处理数量徽章；第一阶段仅站内提醒，不发送邮件、短信或 WhatsApp。
3. 客户可取消尚未领取的询价；已联系或已报价只允许查看状态。
4. 统计新询价、首次响应时长、转报价数量时只按状态事件计算，不从分享次数推断。

验收门槛：个人中心和后台状态一致，权限越权请求返回稳定错误码。

#### P3：清理、兼容和最终验收

技术要点：

1. 删除无引用的选择态 CSS、翻译键和事件监听，保留旧接口兼容测试。
2. 对分享、询价、报价使用独立审计动作名称，确保日志可以还原完整链路。
3. 补齐 API、数据结构、部署、数据库迁移和 NAS 恢复文档。
4. 执行全部自动化测试、数据库维护检查、PDF 文本检查和浏览器人工验收。
5. 本地验收通过后再提交 Git；Git 版本确认后才允许同步 Albert-NAS 或 BOTEN-NAS。

最终验收门槛：不存在分享自动生成询价、询价自动暴露报价、工作稿修改影响已发送报价、部分删除或重复询价等情况。

### 12.11 风险与回滚策略

| 风险 | 控制方案 | 回滚点 |
|---|---|---|
| 购物车取消选择态后旧 JS 仍读取 `selectedCartIds` | 先建立前端契约测试，再删除状态和监听 | 恢复前端文件，不回滚数据库 |
| 登录成功后误自动提交 | 待办动作只能打开确认卡片，创建接口必须由最终提交按钮调用 | 关闭恢复动作开关 |
| 重复询价 | 用户级幂等键、按钮加载锁和数据库唯一约束 | 保留首条，重复结果返回原记录 |
| 当前选配中英文快照不一致 | 服务端分别构建 zh/en，不接受前端翻译文本 | 标记快照异常并拒绝提交 |
| 目录项目后续失效 | 保存历史快照并在后台标记风险，不自动删除 | 无需回滚历史询价 |
| 两名业务员同时领取 | `version` 乐观锁和条件更新 | 冲突方刷新记录 |
| 转报价产生重复草稿 | `converted_quote_id` 与服务端幂等转换 | 返回已有草稿 |
| 新迁移影响历史数据 | 只新增表和可空字段，执行前备份并验证恢复 | 使用备份恢复，不执行破坏性 downgrade |

### 12.12 分阶段验收建议

1. **第一次验收：数据安全。** 报价 revision、客户可见版本、询价表和接口权限。
2. **第二次验收：用户端。** 登录恢复、购物车全量分享/PDF、卡片删除和两个询价入口。
3. **第三次验收：管理后台。** 询价搜索、领取、分配、状态流转和转报价。
4. **最终验收：全链路。** 分享不触发询价；询价转报价；报价正式发送；客户查看固定 revision 和 PDF。
