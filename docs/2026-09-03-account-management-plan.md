# BOTEN 账号管理全链路整改计划

日期：2026-09-03  
范围：管理后台账号管理，包括新增、编辑、联系方式维护、角色调整、密码重置、启用、停用、归档、恢复、错误处理、提示翻译和自动化测试。

## 实施结果（2026-09-03）

状态：计划内开发任务已完成，本地 E 盘版本已通过数据库迁移、自动化回归和浏览器验收；尚未同步 Git 或部署到 BOTEN-NAS。

- 完成结构化账号错误协议：响应包含稳定 `error.code`、字段名、参数和 `request_id`，支持中文与英文消息；429 保留 `Retry-After`，500 不再向界面暴露服务器内部信息。
- 修复联系方式显式清空逻辑；邮箱和手机号至少保留一项，重复邮箱与重复手机号分别定位到具体字段。
- 敏感字段（邮箱、手机号、国家、角色、密码）、停用和归档均撤销目标账号全部会话；仅修改显示名称不注销。
- 后台账号维护已拆为“编辑资料、修改角色、重置密码、启用/停用、归档/恢复”独立流程，并加入字段级提示、失败焦点、按钮忙碌状态、未保存确认和关闭后焦点恢复。
- 账号列表同时显示邮箱和完整国际手机号，并支持关键词、角色、状态、归档筛选及服务端分页；筛选和页码写入 URL。
- 写入成功后先使用响应更新当前行，再后台同步列表；同步失败只提示“操作已保存，但列表同步失败”，不会误报保存失败或重试写操作。
- 采用软归档默认策略：保留联系方式和全部业务历史，归档联系方式暂不允许新账号复用；恢复时重新启用账号。
- 完成账号操作审计与失败审计；不记录密码、令牌或完整表单，只记录字段名、前后状态、错误代码和请求编号。
- 新增乐观锁 `users.version`，过期表单返回 `409 ACCOUNT_VERSION_CONFLICT`，避免多人覆盖。
- 数据库已在备份 `backups/boten-20260903-081814-853308.db` 后升级至 Alembic `20260903_0008 (head)`，`quick_check` 通过。
- 全量测试共 42 项通过；另完成本地浏览器页面、编辑弹窗、字段级邮箱错误及未保存确认的实际验收。
- 用户端登录失败重试链路已同步整改：接入结构化错误码和中英文提示，增加 15 秒超时、重复提交保护、按钮 `aria-busy` 释放、错误字段聚焦及重新输入时清除旧错误。独立浏览器实测“错误密码失败 → 修改密码 → 再次提交”可正常登录；中英文提示均已核对。

## 实施前结论（已整改）

现有新增账号、编辑账号、管理员重置密码、启用/停用、自我停用保护和最后一个管理员保护已经具备基础实现，相关现有测试可以通过。但目前仍存在以下关键缺口：

- 清空邮箱或手机号时，后端仓库层会过滤 `None`，数据库中的旧值可能无法真正清除。
- 保存成功后如果列表重新加载失败，前端会把整个流程显示为保存失败，可能导致重复操作。
- 后台尚无正式的账号归档、恢复或删除链路。
- 后端错误提示中英文混用，前端直接显示 API `detail`，无法稳定翻译和定位字段。
- 修改角色、邮箱或手机号后，目标用户的既有会话没有统一撤销。
- 联系方式、权限调整和密码重置集中在一个弹窗内，容易误操作，失败提示也不够具体。

## 优先级与执行顺序

### 第一阶段：P0 数据正确性与操作幂等

#### 1. 修复联系方式无法清空

目标：允许管理员清空邮箱或手机号，但任何账号至少保留一种登录联系方式。

技术方案：

- 修改 `backend/user_repository.py`，区分“字段未提交”和“字段明确提交为空”。
- `email`、`phone`、`phone_country` 允许显式更新为数据库 `NULL`。
- 密码字段继续保持“空值表示不修改”，不能套用联系方式的空值规则。
- 联系方式校验、唯一性校验、数据库写入放在同一事务中。
- 接口返回数据库实际保存后的完整账号对象。

验收：

- 可以清空邮箱并保留手机号。
- 可以清空手机号和国家并保留邮箱。
- 同时清空邮箱和手机号时阻止保存，并定位到联系方式区域。

#### 2. 分离“保存结果”和“列表刷新结果”

目标：避免账号已经保存，但页面提示保存失败。

技术方案：

- `POST/PATCH` 成功后立即使用接口响应更新 `state.users` 和当前表格行。
- 先显示“账号已保存”，随后在后台重新同步完整列表。
- 如果同步失败，提示“账号已保存，但列表刷新失败，请手动刷新”，不得显示为保存失败。
- 写操作不自动重试，防止重复创建或重复修改。
- 保存按钮在请求期间显示“正在保存…”并使用 `aria-busy`。

验收：

- 模拟写入成功、刷新失败时，表格仍显示新数据。
- 连续点击保存不会产生重复账号。

#### 3. 统一安全敏感修改后的会话撤销

目标：权限或登录凭据改变后，旧会话不能继续使用旧身份。

技术方案：

- 修改密码、角色、邮箱、手机号或国家后，撤销目标账号全部会话。
- 停用和归档账号时继续强制撤销全部会话。
- 普通显示名称修改不强制退出。
- 修改当前管理员自己的登录联系方式后，前端清理令牌并返回登录页。
- 角色变更在事务提交后立即生效。

验收：

- 敏感字段修改后，旧 Token 请求 `/api/v1/auth/me` 返回 401。
- 仅修改姓名时当前会话仍有效。

### 第二阶段：P1 统一错误协议与中英文提示

#### 4. 建立结构化错误响应

目标：前端不再依赖后端自然语言判断错误类型。

建议响应：

```json
{
  "error": {
    "code": "ACCOUNT_EMAIL_DUPLICATE",
    "field": "email",
    "params": {}
  },
  "request_id": "..."
}
```

首批错误代码：

- `ACCOUNT_NOT_FOUND`
- `ACCOUNT_EMAIL_INVALID`
- `ACCOUNT_EMAIL_DUPLICATE`
- `ACCOUNT_PHONE_INVALID`
- `ACCOUNT_PHONE_DUPLICATE`
- `ACCOUNT_PHONE_COUNTRY_INVALID`
- `ACCOUNT_CONTACT_REQUIRED`
- `ACCOUNT_NAME_REQUIRED`
- `ACCOUNT_PASSWORD_TOO_SHORT`
- `ACCOUNT_PASSWORD_TOO_LONG`
- `ACCOUNT_ROLE_INVALID`
- `ACCOUNT_SELF_DISABLE_FORBIDDEN`
- `ACCOUNT_SELF_ROLE_CHANGE_FORBIDDEN`
- `ACCOUNT_LAST_ADMIN_REQUIRED`
- `ACCOUNT_SESSION_EXPIRED`
- `ACCOUNT_PERMISSION_DENIED`
- `REQUEST_TIMEOUT`
- `NETWORK_UNAVAILABLE`
- `SERVER_UNAVAILABLE`

技术方案：

- 增加账号领域异常类型，包含 `code`、`field`、`status_code` 和可选参数。
- FastAPI 增加统一异常处理器，将 Pydantic 校验错误转换为同一结构。
- 前端增加 `accountErrorText(code, language, params)`，提供完整的 `zh-CN` 和 `en` 字典。
- 后台目录内容语言 `catalogLanguage` 与后台界面提示语言分离；目录中英文切换不能改变账号操作提示语言。
- 未识别错误显示安全的通用提示和 `request_id`，不把数据库或服务器异常原文暴露给用户。

#### 5. 细化网络、权限和字段错误

技术方案：

- 401：登录状态失效，请重新登录。
- 403：当前账号没有执行此操作的权限。
- 404：账号已不存在，刷新列表后重试。
- 409：明确标记邮箱重复或手机号重复。
- 422：显示到对应字段下方，并聚焦第一个错误字段。
- 429：提示请求过于频繁和建议等待时间。
- 超时：提示服务器响应超时，可安全重试。
- 网络中断：提示检查网络或 NAS 服务状态。
- 500：提示服务器处理失败并显示请求编号。

界面要求：

- 成功消息使用 `role="status"` 和 `aria-live="polite"`。
- 失败消息使用 `role="alert"`。
- Toast 只用于全局状态；输入错误必须显示在对应字段附近。
- 错误提示必须包含问题、受影响账号和下一步处理建议。

### 第三阶段：P1 账号维护界面重构

#### 6. 拆分账号操作

将现有单一编辑弹窗拆为：

1. 编辑资料：姓名、邮箱、国家、区号和手机号。
2. 调整权限：角色修改及权限影响说明。
3. 重置密码：独立弹窗，不回显密码，提交后撤销目标账号会话。
4. 启用/停用：保留二次确认，提示会话撤销影响。

技术方案：

- 账号表格操作保留“编辑”，其他操作收入“更多”菜单。
- 角色升级、角色降级、密码重置和停用使用明确的确认弹窗。
- 弹窗关闭时检测脏数据；存在未保存修改时提示确认。
- 打开弹窗后聚焦第一个可编辑字段，关闭后恢复到原操作按钮。
- 弹窗内容区域独立滚动并使用 `overscroll-behavior: contain`，头部和底部操作区固定。

#### 7. 完善账号列表信息

技术方案：

- 联系方式列同时显示邮箱和完整国际手机号，不再二选一。
- 增加姓名、邮箱和手机号关键词搜索。
- 增加角色、启用状态和归档状态筛选。
- 筛选按钮补充 `aria-pressed`。
- 数据量超过 50 条时改为服务端分页，URL 保存筛选和页码状态。
- 每一行具有独立的处理状态与失败重试入口。

### 第四阶段：P2 账号归档与恢复

#### 8. 使用归档代替直接物理删除

原因：账号关联配置单、分享、报价和审计记录，直接删除可能导致业务数据级联丢失。

数据方案：

- 新增 `users.deleted_at`。
- 新增 `users.deleted_by`。
- 新增 `users.delete_reason`。
- 归档时设置 `enabled = 0` 并撤销全部会话。
- 默认账号列表不显示已归档账号。
- 提供“查看已归档账号”和“恢复账号”。
- 禁止归档自己以及最后一个可用管理员。

已采用策略：

- 归档时不清除邮箱和手机号。
- 已归档账号的邮箱或手机号不允许被新账号重新使用。
- 账号和业务记录暂长期保留；后续如建立正式数据保留制度，再单独增加匿名化和清理任务。

默认建议：第一版保留联系方式，不允许重复注册；待明确数据保留政策后再增加匿名化功能。

### 第五阶段：P2 审计、并发与可维护性

#### 9. 强化账号操作审计

- 记录创建、资料修改、角色调整、密码重置、启用、停用、归档和恢复。
- 审计只记录变更字段名称及角色/状态前后值，不记录密码和完整表单正文。
- 对权限拒绝、最后管理员保护等重要失败操作记录状态码和错误代码。
- 给每次请求生成 `request_id`，便于界面提示与服务器日志关联。

#### 10. 防止多人同时覆盖修改

- 更新接口提交当前记录的 `updated_at` 或版本号。
- 如果服务器版本已变化，返回 409 `ACCOUNT_VERSION_CONFLICT`。
- 页面提示“该账号已被其他管理员修改”，提供重新加载和重新编辑选项。

## 最终验收流程

1. 创建一个用户、一个业务员和一个备用管理员。
2. 分别修改姓名、邮箱、国家、手机号、角色和密码。
3. 验证敏感修改后的旧会话全部失效。
4. 验证重复邮箱、重复手机号、号码长度错误和联系方式为空的提示。
5. 验证当前管理员及最后一个管理员保护。
6. 停用、启用、归档和恢复测试账号。
7. 检查历史配置、分享、报价和审计数据仍完整。
8. 模拟断网、超时和 API 500，核对提示及恢复操作。
9. 完成中英文、键盘、移动端和 200% 缩放验收。

## 实施边界

- P0 和 P1 可以优先执行，不依赖账号归档策略确认。
- P2 已按本文记录的默认保留政策实现；如需匿名化，必须作为独立数据治理任务执行。
- 不直接物理删除用户及其关联业务数据。
- 所有数据库结构变更通过 Alembic 迁移执行，并在迁移前自动备份数据库。
- 不在日志、审计或错误响应中记录密码、令牌或完整表单正文。
